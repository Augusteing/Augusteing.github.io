SLLists

在第三章中，我们构建了 IntList 类，这是一种理论上可以完成列表所有功能的列表数据结构。然而，实际上， IntList 类存在使用起来较为笨拙的问题，导致代码难以阅读和维护。

如果你自己写代码你就会明白了，很丑陋的数据结构

根本问题在于 IntList 类是一种我称之为“裸递归”数据结构。为了正确使用 IntList 类，程序员必须理解并运用递归，即使是在处理简单的列表相关任务时也是如此。这限制了它对初学者的实用性，并且根据 IntList 类提供的辅助方法类型，可能会引入全新的、容易出错的错误类别。

受我们在使用 IntList 类的经验启发，我们现在将构建一个新的 SLList 类，它在很大程度上更接近现代语言中程序员使用的列表实现方式。我们将通过逐步迭代地添加一系列改进来实现这一点

Improvement #3: Public vs. Private

不幸的是，我们的 SLList 可以被绕过，裸露的数据结构（包含所有潜在危险）的原始成员可以被访问。例如，程序员可以轻易地直接修改列表，但却不通过经过儿童测试、母亲认可的 addFirst 方法：

这会导致一个结构不正确的列表，出现无限循环。为了解决这个问题，我们可以修改 SLList 类，使 first 变量使用 private 关键字声明。

私有变量和方法只能被同一文件 .java 中的代码访问，例如在这种情况下 SLList.java 。这意味着下面的 SLLTroubleMaker 类将无法编译，产生一个 first has private access in SLList 错误。(I like troublemaker)

相比之下，任何在 SLList.java 文件中的代码都可以访问 first 变量。

限制访问可能看起来有些傻。毕竟， private 关键字所做的唯一一件事就是阻止那些本来可以编译的程序运行。然而，在大型软件工程项目中， private 关键字是一个宝贵的信号，它表明某些代码部分应该被最终用户忽略（因此无需理解）。

同样地， public 关键字应被视为一种声明，表明该方法将永远像现在一样正常工作。

以类比的方式，一辆汽车有某些 public 特性，例如油门和刹车踏板。在引擎盖下，有 private 关于这些部件如何运作的细节。在燃油汽车中，油门踏板可能控制某种燃油喷射系统，而在电动汽车中，它可能调节提供给电机的电池功率。虽然私有细节可能因车而异，但我们期望所有油门踏板都表现出相同的行为。改变这些细节会让用户感到非常困扰，甚至可能引发严重的事故。

When you create a **public** member (i.e. method or variable), be careful, because you’re effectively committing to supporting that member’s behavior exactly as it is now, forever.

Invariants

不变式是关于数据结构的一个事实，它被保证为真（假设你的代码中没有错误）。

带有哨兵节点的 SLList 至少具有以下不变式：

  • sentinel 指针始终指向一个哨兵节点。
  • 如果存在，则最前面的元素始终位于 sentinel.next.item 。
  • size 变量始终表示已添加的元素总数。
    不变量使得代码更容易理解，并且在确保代码正确运行时也提供了具体的目标。
