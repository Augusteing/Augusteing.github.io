Testing and Selection Sort

对于中级到高级程序员来说，最重要的技能之一就是能够判断自己的代码是否正确。在本章中，我们将讨论如何编写测试来评估代码的正确性。在这个过程中，我们还将讨论一种名为选择排序的排序算法。

A New Way

当你编写程序时，它可能会有错误。在课堂环境中，你通过用户交互、代码分析和自动评分器测试的组合来获得代码正确性的信心，在许多情况下，尤其是作为你获得分数的方式，自动评分器测试最为重要。（分数万岁是吧）

自动评分器当然不是魔法。它们是讲师编写的代码，本质上与你们正在编写的代码并没有太大区别。在现实世界中，这些测试是由程序员自己编写的，而不是某个像 Josh-Hug 一样仁慈的第三方。（Josh-Hug是本课程的教授）

在这一章中，我们将探讨如何编写自己的测试。我们的目标将是创建一个名为 Sort 的类，该类提供一个名为 sort(String[] x) 的方法，该方法会破坏性地对数组 x 中的字符串进行排序。

作为一种全新的思维方式，我们将首先编写 testSort() ，只有在完成测试之后，我们才会继续编写实际的排序代码。

重要提示：你可能会问“为什么你要遍历整个数组？为什么不用 == 来检查数组是否相等？”原因在于，当我们测试两个对象的相等性时，不能简单地使用 == 运算符。 == 运算符比较内存盒子中的字面值，例如 input == expected 会测试 input 和 expected 的地址是否相同，而不是测试数组中的值是否相同。相反，我们在 testSort 中使用了循环，并打印出第一个不匹配的地方。你也可以使用内置方法 java.util.Arrays.equals 来代替循环。

Selection Sort

在我们可以编写一个 Sort.sort 方法之前，我们需要一些排序算法。也许最简单的排序算法是”选择排序。”选择排序包括三个步骤：

  • 找到最小项
  • 把它移到前面。
  • 对剩下的 N-1 个项目进行选择排序（不触及第一个项目）。

例如，假设我们有一个数组 {6, 3, 7, 2, 8, 1} 。这个数组中最小的元素是 1 ，因此我们会将 1 移到最前面。有两种自然的方法来做这件事：一种是把 1 放在前面，然后把所有的数字都滑过去，即 {1, 6, 3, 7, 2, 8} 。然而，更高效的方法是直接将 1 与原来的最前面的元素（在这个例子中是 6 ）交换，得到 {1, 3, 7, 2, 8, 6} 。

我们会简单地重复相同的过程来处理剩余的数字，即 ... 3, 7, 2, 8, 6} 中最小的元素是 2 。将其交换到最前面，我们得到 {1, 2, 7, 3, 8, 6} 。重复这个过程直到我们得到一个排序好的数组，我们会得到 {1, 2, 3, 7, 8, 6} ，然后是 {1, 2, 3, 6, 8, 7} ，最后是 {1, 2, 3, 6, 7, 8} 。

我们可以通过使用在第 2.4 章中最初引入的不变性概念，从数学上证明这个排序算法在任何数组上的正确性，尽管我们不会在本书中这样做。在进行下一步之前，尝试自己写出一个短数字数组，并对其进行选择排序，这样你就能确保你理解了这个概念。

Reflections on the Development Process

当你编写和调试程序时，你经常会发现自己在不同上下文之间切换。试图同时在大脑中记住太多内容，在最坏的情况下会导致灾难，在最好的情况下也会导致进展缓慢。

拥有一套自动化测试有助于减轻这种认知负担。例如，我们正在编写 sort 时，突然发现 findSmallest 中存在一个 bug。我们能够切换到考虑 findSmallest ，并使用我们的 testFindSmallest 方法确认它是正确的，然后切换回 sort 。这与更简单的方法形成鲜明对比，那种方法只是反复调用 sort ，试图判断整体算法的行为是否表明 findSmallest 方法是正确的。

打个比方，你可以通过坐飞机、起飞、跳伞并拉下拉索，看看降落伞是否打开来测试降落伞的拉索是否有效。然而，你也可以直接在地面拉一下，看看会发生什么。同样，使用 sort 来尝试 findSmallest 也是不必要的。

如本章前面所述，测试还允许你对你程序的基本部分建立信心，这样如果出了问题，你就能更好地知道从哪里开始查找

最后，测试使重构代码变得更容易。假设你决定重写 findSmallest ，使其更快或更易读。我们可以通过做出所需更改并查看测试是否仍然有效来安全地这样做。

Testing Philosophy  测试哲学

**Correctness Tool #1: Autograder

让我们回到起点。自动评分器很可能是你接触到的第一个正确性工具。我们的自动评分器实际上是基于 JUnit 加上一些额外的自定义库构建的。

自动评分系统有一些显著的好处。最重要的是，它能帮你验证正确性，让你不必费心编写所有自己的测试，从而节省时间和精力。它还通过提供有吸引力的分数来激励学生追求正确性，使评估过程游戏化。但这也可能适得其反，如果学生花费过多时间追逐那些实际上不会影响他们的成绩或学习进度的分数。

然而，自动评分系统在现实中并不存在，依赖自动评分系统可能会养成不良习惯。你的工作流程会被频繁上传代码并等待自动评分系统运行所阻碍。自动评分驱动开发是这种情况的极端版本，学生编写所有代码，修复编译错误，然后提交给自动评分系统。收到错误后，学生可能会尝试进行一些修改，添加打印语句，再次提交。如此反复。最终，如果你依赖自动评分系统，你将无法控制自己的工作流程或代码。

**Correctness Tool #2: JUnit Tests

正如我们所见，JUnit 测试为你打开了一个新世界。你不再依赖别人编写的自动评分器，而是为你的程序的每一部分编写测试。我们将每一部分称为一个单元。这让你对你的代码的每个单元都有信心——你可以依赖它们。这也帮助你减少调试时间，因为你可以一次专注于一个代码单元（通常是一个单独的方法）。单元测试还迫使你明确每个代码单元应该完成什么任务。

然而，单元测试也有一些缺点。首先，编写全面的测试需要花费时间。很容易写出不完整的单元测试，从而给你的代码带来虚假的信心。此外，为依赖于其他单元的单元编写测试也很困难（考虑一下你的 addFirst 中的 LinkedListDeque 方法）。

  4. Write code that passes the test. Yay!
    编写通过该测试的代码。太棒了！

  5. Optional: refactor code to make it faster, cleaner, etc. Except now we have a reference to tests that should pass.
    可选：重构代码使其更快、更简洁等。但现在我们有参考需要通过的测试。

Test-Driven Development is not required in this class and may not be your style but unit testing in general is most definitely a good idea.
测试驱动开发在本课程中不是必需的，也可能不是你的风格，但单元测试总的来说绝对是个好主意。

**Correctness Tool #3: Integration Testing

单元测试很棒，但我们还应该确保这些单元能正确地协同工作（不像这个梗图）。集成测试验证组件能否正确地交互。实际上 JUnit 可以用在这方面。你可以想象单元测试是最细致的，而集成测试是比这更高层次的抽象。
集成测试的挑战在于手动执行起来很繁琐，而自动化又很困难。从高层次抽象来看，很容易错过微妙或罕见错误。

总结来说，你确实应该写测试，但只有在它们可能有用的时候才写！借鉴测试驱动开发（TDD）的思路，在编写代码之前先写测试在某些情况下也非常有帮助。
