回忆一下我们上周创建的两个列表类：SLList 和 AList。如果你查看它们的文档，你会发现它们非常相似。事实上，它们所有的支持方法都是一样的！

这实际上在 Java 中是允许的！这被称为方法重载。当你调用 WordUtils.longest 时，Java 会根据你提供的参数类型知道运行哪一个。如果你提供一个 AList，它将调用 AList 的方法。对于 SLList 也是同样的情况。

Java 足够智能，能够处理不同类型的两个相同方法，这很好，但重载有几个缺点：

  • 它非常重复且丑陋，因为你现在有两个几乎相同的代码块。
  • 需要维护更多的代码，这意味着如果你想要对 longest 方法进行小的更改，例如修正一个错误，你需要在每种类型的列表的方法中更改它。
  • 如果我们想创建更多种类的列表，我们就必须为每个新的列表类复制方法。

Hypernyms, Hyponyms, and Interface Inheritance

在英语语言和日常生活中，词语和对象之间存在逻辑层次关系。

狗是被称为 poodle、malamute、husky 等的上位词。在相反的方向上，poodle、malamute 和 husky 是狗的下位词。

这些词语形成了一个”是”关系层次：

  • 一只贵宾犬”是”一只狗
  •  一只狗”是”一种犬科动物
  • 一种犬科动物”是”一种食肉动物
  • 一个食肉动物 “是” 一种动物

SLLists 和 ALists 也遵循相同的层级关系！SLList 和 AList 都是更通用列表的次级分类。

我们将在 Java 中形式化这种关系：如果 SLList 是 List61B 的次级分类，那么 SLList 类是 List61B 类的子类，而 List61B 类是 SLList 类的超类。


在 Java 中，为了表达这种层次结构，我们需要做两件事：

  • 步骤 1：为一般列表超类定义一个类型——我们将选择名称 List61B。
  • 步骤 2：指定 SLList 和 AList 是该类型的下位类。

新的 List61B 是 Java 中称为接口的东西。它本质上是一个合同，指定了列表必须能够做什么，但它不提供这些行为的任何实现。你能想到为什么吗？

这是我们的 List61B 接口。此时，我们已经满足了建立关系层次结构的第一步：创建一个超类。

现在，为了完成第二步，我们需要指定 AList 和 SLList 是 List61B 类的下位词。在 Java 中，我们在类定义中定义这种关系。

我们将添加到

public class AList<Item> {...}

一个定义关系的词：实现。

public class AList<Item> implements List61B<Item>{...}

implements List61B<Item> 本质上是一种承诺。AList 在说”我承诺我将拥有并定义 List61B 接口中指定的所有属性和行为”

现在我们可以编辑我们的 longest 方法在 WordUtils 中，以接收一个 List61B。因为 AList 和 SLList 共享一个”是”关系。

Overriding

我们承诺将在 AList 和 SLList 类中实现 List61B 中指定的方法，那么让我们继续做这件事。

在子类中实现所需函数时，包括方法签名顶部的 @Override 标签很有用（实际上在 61B 中是必需的）。这里，我们只对其中一个方法做了这样的处理。

值得注意的是，即使你不包括这个标签，你仍然在重写方法。所以从技术上讲，你不必包括它。然而，包括这个标签可以作为程序员的一种保护措施，通过提醒编译器你打算重写这个方法。你可能会问，这有什么帮助？嗯，这有点像有一个校对员！如果过程中出了什么问题，编译器会告诉你。

假设你想重写 addLast 方法。如果你打字错误，不小心写成了 addLsat 怎么办？如果你不包含@Override 标签，你可能不会发现这个错误，这会使调试过程变得更加困难和痛苦。而如果你包含@Override，编译器会停止并提示你在程序运行之前修复你的错误。

Interface Inheritance

接口继承指的是子类继承超类所有的方法/行为的一种关系。正如我们在“下位词和上位词”部分定义的 List61B 类，接口包含所有方法签名，但不包含实现。具体实现由子类提供。

这种继承也是多代性的。这意味着如果我们有像图 4.1.1 那样的超类/子类关系长链，AList 不仅继承 List61B 的方法，还继承所有位于其上的其他类，一直到最高超类（即 AList 继承自 Collection）。

Implementation vs. Interface Inheritance

我们如何区分”接口继承”和”实现继承”？好吧，你可以使用这个简单的区分：

接口继承（是什么）：简单告诉子类能做什么。

  • 例如）所有列表都应该能打印自己，具体如何实现由它们自己决定。

实现继承（怎么做）：告诉子类如何实现它们的行为。

  • 例如，列表应该（默认情况下）以这种方式打印自己：按顺序获取每个元素，然后打印它们。

Abstract Data Types

抽象数据类型（ADT）仅通过它支持的操作（行为）来定义，而不是通过它的具体实现代码来定义

笔者的浅薄解释：

    1. “仅由操作定义”：ADT 描述了一组操作（例如“添加元素”、“删除元素”、“检查是否为空”），以及这些操作应该具有的行为（例如“添加后集合包含该元素”）。它就像一个契约或接口，只说明你可以调用哪些方法、这些方法接受什么参数、返回什么结果，以及它们应该做什么，但不涉及内部如何实现。
    1. “不由实现定义”：同一个 ADT 可以有多种不同的实现方式。例如，“栈”这个 ADT 可以用数组实现，也可以用链表实现。尽管内部数据结构完全不同，但它们都提供了相同的操作（push、pop、peek），并且这些操作的行为符合栈的后进先出（LIFO）规则。因此，实现不影响 ADT 的定义，它只是完成操作的具体手段。

总结来说：ADT 仅仅是一种概念，而不是一种实现。

例如在项目 1A 中，我们开发了一个 ArrayDeque 和一个 LinkedListDeque ，它们具有相同的方法，但方法的编写方式差异很大。在这种情况下，我们称 ArrayDeque 和 LinkedListDeque 是 Deque ADT 的实现。

  • 栈：支持元素后进先出检索的结构

  • push(int x): puts x on the top of the stack
    push(int x) : 将 x 放在栈顶

  • int pop(): takes the element on the top of the stack
    int pop() : 取出栈顶元素

  • 列表：一组有序元素

  • add(int i): adds an element
    add(int i) : 添加一个元素

  • int get(int i): gets element at index i
    int get(int i) : 获取索引为 i 的元素

  • 集合：一组无序的唯一元素（不重复）

  • add(int i): adds an element
    add(int i) : 添加一个元素

  • contains(int i): returns a boolean for whether or not the set contains the value
    contains(int i) : 返回一个布尔值，表示集合是否包含该值

  • 映射：键值对集合

  • put(K key, V value): puts a key value pair into the map
    put(K key, V value) : 将键值对放入映射中

  • V get(K key): gets the value corresponding to the key
    V get(K key) : 获取与键对应的值

注意：加粗的 ADT 是某个更大接口的子接口，该接口称为 Collections.
