ArrayList

在本节中，我们将构建一个名为 AList 的新类，它可以用来存储任意长度的数据列表，类似于我们的 DLList 。与 DLList 不同， AList 将使用数组来存储数据，而不是链表。

Linked List Performance Puzzle

假设我们想要为 DLList 编写一个名为 int get(int i) 的新方法。为什么 get 对于长列表来说比 getLast 慢？在什么输入下它会特别慢？

您可能会发现下面的图形对于思考您的答案很有用。

Linked List Performance Puzzle Solution

结果证明，无论你多么聪明，如果我们使用 2.3 节中描述的双向链表结构， get 方法通常会比 getBack 方法慢。

这是因为，由于我们只有列表第一个和最后一个元素的引用，我们总需要从前面或后面遍历列表才能到达我们试图检索的元素。例如，如果我们想在一个长度为 10,000 的列表中获取第 417 个元素，我们将不得不跨越 417 个前向链接才能到达我们想要的元素。

在最坏的情况下，该元素位于列表正中间，我们将需要遍历与列表长度成比例数量的元素（具体来说，是列表元素数量除以二）。换句话说，我们的 get 的最坏情况执行时间是整个列表大小的线性函数。这与 getBack 的运行时形成对比， getBack 的运行时与列表大小无关，始终是常数。在本课程后面，我们将用大 O 和大 Theta 符号正式定义运行时。目前，我们将坚持非正式的理解。

removeLast

我们需要支持的最后一个操作是 removeLast 。在开始之前，我们做一个关键观察：对列表的任何更改都必须反映在我们实现中的一个或多个内存框的更改中。

这可能看起来很明显，但其中蕴含着深刻的意义。列表是一个抽象概念，而 size 、 items 和 items[i] 内存框是这个概念的具体表示。用户使用我们提供的抽象（ addLast 、 removeLast ）尝试对列表进行的任何更改，都必须以符合用户期望的方式反映在这些内存框的某些变化中。我们的不变式为我们提供了关于这些变化应该是什么样子的指导。

Analyzing the Naive Resizing Array

我们在上一节中尝试的方法性能非常差。通过运行一个简单的计算实验，我们调用 addLast 100,000 次，发现 SLList 完成得如此之快，以至于我们甚至无法测量它。相比之下，我们的基于数组的列表需要几秒钟的时间。

练习 2.5.5：假设我们有一个大小为 100 的数组。如果我们调用两次 insertBack，在整个过程中总共需要创建和填充多少个框？假设垃圾收集在数组最后一次引用丢失时立即发生，那么在任何时候我们总共有多少个框？

练习 2.5.6：从一个大小为 100 的数组开始，如果我们调用 addLast 1,000 次，大约会创建并填充多少个内存框？

A:显然地，有100 + 101 + …. + 1000；

创建所有这些内存盒子并复制它们的内容需要时间。在下方的图中，我们绘制了 SLList 和基于简单调整大小数组的列表的总时间与操作次数的关系。SLList 显示为一条直线，这意味着对于每个 add 操作，列表需要相同的时间增量。这意味着每个单独的操作都只需要常数时间！你也可以这样理解：图是线性的，这表明每个操作都需要常数时间，因为常数的积分是一条直线。

相比之下，基于简单调整大小数组列表呈现出抛物线形状，表明每次操作都需要线性时间，因为直线的积分是抛物线。这具有重大的现实意义。对于插入 100,000 个项目，我们可以通过计算 N^2/N 的比值来粗略地计算出需要多长时间。将 100,000 个项目插入我们的数组列表需要(100,000^2)/100,000，即 100,000 倍的时间。这显然是不可接受的。

Memory Performance

我们的 AList 几乎完成了，但我们有一个主要问题。假设我们插入 1,000,000,000 个项目，然后后来删除 990,000,000 个项目。在这种情况下，我们只会使用 10,000,000 个我们的内存框，留下 99%完全未被使用。

要解决这个问题，我们也可以在数组看起来空的时候缩小它。具体来说，我们定义一个”使用率”R，它等于列表的大小除以 items 数组的长度。例如，在下图中，使用率是 0.04。

我们做出的另一个改变是，我们将我们”删除”的任何项目置为 null。而之前，我们没有理由将已删除的元素置零，但对于通用对象，我们确实需要将存储对象的引用置为 null。这是为了避免”游荡”。回想一下，Java 只有在最后一个引用丢失时才会销毁对象。如果我们未能置为 null 引用，那么 Java 将不会垃圾回收已添加到列表中的对象。

这是一个微妙且你可能不会察觉的性能问题，但在某些情况下可能会导致大量内存浪费。
