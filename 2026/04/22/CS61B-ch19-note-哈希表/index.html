Introduction to Hashing: Data Indexed Arrays

#cs61b

到目前为止，我们在课程中已经看到了许多将事物存储在数据结构中的方法，但它们在运行时效率并不总是最高。现在，让我们来介绍一种令人难以置信的数据结构，它可以在其中提供插入、删除和包含检查，无论其内部有多少元素（即使有数百万个项目）——在最佳情况下，所有操作都在 O(1)运行时间内完成！听起来太好了，以至于不真实？

在本章中，我们将探索哈希的魔力，看看这是如何实现的。

快速回顾

我们已研究过一些存储数据结构，他们的高效搜索由一些数据结构提供支持。我们首先研究了二叉搜索树，然后通过 2-3 树使其保持平衡。

但是他们存在着局限（即使2-3数也有局限）

1.它们要求元素必须可比较。在二叉搜索树中，你如何决定新元素的位置？你必须回答“你比根节点小还是大”的问题？对于某些对象，这个问题可能没有意义。
2.它们提供了 $Θ(logN)$ 的复杂度。这好吗？当然好。但也许我们可以做得更好。

ArraySet

如果我们只考虑一个存储整数的ArraySet，那么对于其的两个操作 add contains 具有以下运行时

  • add 添加操作将变得非常简单，为 $\theta(1)$ 因为数组的性质。
  • contains 操作将会变得非常复杂，因为我们需要遍历数组才能完成这项工作。

所以，我们考虑使用分组的思想来制作这个集合。我们首先考虑的是以数字的最后一位字母为划分的依据，这样会将所有要存储的数字分为 0-9 共10类。

这个办法在小的数据集上会有效的减少 contains 操作所需要的时间，但是当数字的时候， $\theta(n)$ 的时间复杂度却会保持不变，所以我们需要新的思路。

解决办法

一个有效的思考是：当我们的数据量 $N$ 增加时，我们同时会增加我们的分组的数量 $M$ ，对于这种算法，具体的实现方式是按照 $M$ 的取模来分组。

一旦使用取模这种运算，所有的数字被分为了 0 -> M-1 组。那我们如何随着 N 的增加来增加 M呢？

我们规定：一旦 $N / M$ 的数值大于某个常数 $k$，我们就将 $M$ 的值翻倍。（你是否想到了 ArraySet 的扩容实现？

该图片展示了 $k >= 1.5$ 的情况。

近似的这种算法被认为具有常数时间的复杂度，因为如果我们限制了 N / M 的数值，而且数据大体上分布均匀的话，我们可以理解为每一个项中都平均有 N / M的数据量，而 N/M为常数。

上述的做法很有效！但是很遗憾的是现实世界不止有整数，还有字符串、浮点数、你的狗等等许多对象。我们不能为每一类都设计好一种集合，这既不优雅也不高效。所以，我们打算让集合只处理整数，而要存储的对象自己写下函数如何将自身转化为整数。

快速提示：在 Java 中， Math.floorMod 函数将执行模运算，同时正确处理负整数，而 % 则不会。

更大问题

但是很遗憾的是，现实世界不只有小写的英文字母（仅仅有26个）。如果我们想编码更多的对象就需要更多位的基底。


比如这个日文名字（中国汉字），其以40959为底，会产生一个十分十分巨大的数字啊。这种数字实际上很难在计算机中存储。Java 的整数类型只允许存储 ±2 ^ 32 ± 1的数字而已。

日文名 "横田誠司" 按 Base-31 计算，结果是 **839,611,422（没有超载，安全存下）。乱码字符串 "±EreWn" 按公式计算，理论值高达 51 亿（5,134,578,718）。 因为 51 亿远超 21.4 亿的上限，底层二进制发生了溢出和截断。截断后剩下的值，竟然极其巧合地也是 839,611,422**。

在工业级编程中，哈希冲突（Hash Collision）不是偶然，而是不可避免的宿命。

可惜了兄弟可惜

有效哈希

  • 确定性：对于相等的两个对象 A 和 B（ A.equals(B) == true ），它们的 hashCode() 函数应该具有相同的哈希码。这也意味着哈希函数不能依赖于对象中未反映在 .equals() 方法中的属性。
  • 一致性： hashCode() 函数在同一个对象实例上每次调用时都返回相同的整数。这意味着 hashCode() 函数必须独立于时间/秒表、随机数生成器或任何在同一个对象实例上多次调用 hashCode() 函数时不会给我们提供一致 hashCode() 的方法。

请注意，没有要求说明不同对象应该具有不同的哈希函数值。

好的哈希

  • 哈希函数必须是有效的。
  • hashCode() 函数值应在所有整数的集合中尽可能均匀分布。
  • hashCode() 函数应相对快速计算[理想情况下为 O(1)的常量时间数学运算]
