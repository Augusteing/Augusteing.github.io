API

在理想的世界中，我们认为一个大型项目应该完全被拆分为不同的模块。

但是这很难实现，因为为了实现不同的功能，总会出现模块之间耦合的情况。

一个 Java 类的API可以分为：

  1. 形式化 API (Formal Part)：指方法签名的列表（The list of method signatures）。这包括方法名、参数类型列表和返回值类型。
  2. 非形式化 API (Informal Part)：指那些编译器无法强制执行的 API 使用规则。这些规则只能通过代码注释（Comments）来详细说明。
    1. 时序与状态依赖：例如，使用迭代器时，要求必须先调用 hasNext 才能调用 next 以保证正常工作。编译器不会阻止你连续调用两次 next，但运行时会崩溃。
    2. 隐藏的异常逻辑：例如，某个 add 方法在遇到 null 输入时会抛出异常。在语法上，传 null 给对象参数是合法的，但在此 API 的业务逻辑中是被禁止的。

静态可变变量（Static mutable variables）会导致“极其可怕且复杂的非形式化规则”

静态可变变量是指：

  • 静态（Static）：使用 static 关键字修饰。它不属于任何一个通过 new 创建的具体对象（实例），而是存在于类本身的内存空间中。全局只有这一份。

  • 可变（Mutable）：它的状态是可以改变的。这包含两种情况：

    • 未加 final 修饰的变量：可以被随时重新赋值（例如 static int count = 0;）。

    • 指向可变对象的 final 变量（隐蔽且危险）：虽然引用本身不能变，但对象内部的数据可以变（例如 static final ArrayList<String> history = new ArrayList<>();，任何代码都可以往里面 add 或 clear 数据）。

好的模块设计

Ousterhout 给出了深层次模块的定义：“最好的模块是那些提供了强大功能，但同时拥有简单 API 的模块。我用‘深’这个词来形容这类模块”。

红黑树集合是一个很好的例子：对外，它只暴露最直观的基础操作：add（添加）、contains（查询）、delete（删除）。

虽然用户调用起来像普通的集合一样简单，但它底层的操作是极其高效的（保证了严谨的 $O(\log N)$ 复杂度）

信息泄露（抽象泄露）

Avatar 应该仅仅管理自身的移动意图。它应当向 World 或 Game 引擎发起移动请求（例如调用类似 world.tryMove(this, west)），由系统来判定该位置能否通行，并由系统去负责改变地图状态（如把硬币变成地板）或更新玩家得分。

时间分解

“时间分解”的定义：指的是系统的代码或模块结构单纯反映了事件发生的时间顺序。开发者在设计类或方法时，顺着用户的操作时间线来写流水账。例如，按照“启动程序 -> 输入随机种子 -> 使用 WASD 移动 -> 保存状态并退出 -> 重启 -> 读取状态”的顺序来切分系统的核心架构。

为什么它是反模式：如果按照时间顺序划分模块（例如拆分成 StartupPhase、PlayingPhase、SavePhase 等类），这些不同时间段的模块必然需要共享底层数据。这就迫使你把本该隐藏的内部数据（如地图的二维数组、玩家坐标）设为 public 暴露出来在各个阶段之间传递，从而导致严重的“信息泄露”和代码高耦合。

实现保存和读取的最优雅方式，不是去序列化每一个瞬间的庞大内存状态，而是仅仅记录“初始随机种子”和完整的“按键历史序列”。
