Introduction

我们这样的人（比如你和我）居住在各自的国家里，并生活在这些国家中。

我们可以把每一个国家看作一个集合（set），而生活在这个国家里的所有人就是这个集合中的元素（elements）。

同一个人不可能在同一时间生活在两个不同的国家。

我们刚刚建立的这个模型，就是一个不相交集合（disjoint set）。

如果两个集合没有共同的元素，那么它们被称为不相交集合。不相交集合（或并查集）数据结构跟踪固定数量的元素，这些元素被划分成若干个不相交的集合。该数据结构有两个操作：

  1. connect(x, y) : 连接 x 和 y 。也称为 union
  2. isConnected(x, y) : 如果 x 和 y 连接（即属于同一集合），则返回 true。

一个不相交集合数据结构包含固定数量的元素，每个元素最初都在自己的子集中。通过调用 connect(x, y) 对某些元素 x 和 y ，我们可以将子集合并在一起。

（你或许会感到疑惑，接下来的例子会让你明白的）

基于这种直觉，让我们正式定义我们的 DisjointSets 接口看起来是怎样的。作为提醒，一个接口决定了数据结构应该具有哪些行为（但不是如何实现这些行为）。以这种方式，任何实现 DisjointSets 接口的类都知道要始终包含以下函数： connect(int p, int q) 和 isConnected(int p, int q) 。目前，我们将只处理非负整数集合。这并不是一个限制，因为在生产环境中，我们可以将整数值分配给任何我们想要表示的事物。

但我们如何存储这些不相交集合的数据，以查看哪个成员属于其对应的集合？我们将使用哪些数据结构来表示这个令人惊叹的数据结构？除了学习如何实现一个有趣的数据结构外，本章还将是一个观察数据结构实现如何演变的良机。在满足之前，我们将讨论不相交集合设计的四次迭代：Quick Find → Quick Union → 带权 Quick Union（WQU）→ 带路径压缩的 WQU。我们将看到设计决策如何极大地影响渐近运行时间和代码复杂度。

快速查找

List of Sets  集合列表

直观上，我们可能会首先考虑将不相交集合表示为一系列集合，例如 List<Set<Integer>> 。

例如，如果我们有 N=6 个元素且尚未有任何连接，我们的集合列表看起来像这样： [{0}, {1}, {2}, {3}, {4}, {5}, {6}] 。看起来不错。然而，考虑如何完成像 connect(5, 6) 这样的操作。我们需要遍历多达 N 个集合来查找 5，遍历 N 个集合来查找 6。我们的运行时间变为 O(N) 。而且，如果你尝试实现这个，代码会相当复杂。

要吸取的教训是，初始设计决策决定了我们的代码复杂性和运行时间。

Quick Union

假设我们优先考虑使 connect 操作快速。我们仍然用数组来表示我们的集合。我们不再为每个元素分配一个 id，而是分配其父元素的索引。如果一个元素没有父元素，那么它是一个’根’，我们分配它一个负值。

对于 QuickUnion，我们定义了一个辅助函数 find(int item) ，它返回树 item 所在的根。例如，对于上面的集合， find(4) == 0 、 find(1) == 0 、 find(5) == 3 等。每个元素都有一个唯一的根。

connect(x, y)

要连接两个元素，我们找到每个元素所属的集合（它们各自树的根），并将其中一个设为另一个的子节点。示例：

connect(5, 2):

  1. find(5) -> 3

  2. find(2) -> 0

  3. 将 find(5) 的值设置为 find(2) ，即 parent[3] = 0

在最好的情况下，如果 x 和 y 都是它们各自的树的根，那么 connect(x, y) 只需让 x 指向 y ，这是一个 Θ(1) 操作！（因此得名 QuickUnion）

如果两个元素属于同一个集合，那么它们将位于同一棵树中。因此，它们将拥有相同的根。所以对于 isConnected(x, y) 我们只需检查 find(x) == find(y) 。

N = DisjointSets 数据结构中元素的数量

从运行时图表来看，QuickUnion 似乎比 QuickFind 更差！然而需要注意的是，O(N)只是一个上界。当我们的树是平衡的时候， connect 和 isConnected 都能表现得相当好。在下一节中，我们将看到如何保证它们表现良好。

Weighted Quick Union (WQU)

改进快速联合算法的关键在于一个核心洞察：每当我们调用 find 时，都必须爬到一棵树的根。因此，树越短，所需时间越快！

新规则：每当我们调用 connect 时，我们总是将较小树的根连接到较大树。

遵循这个规则将使您的树的最大高度为 $logN$ ，其中 N 是我们不相交集合中元素的数量。这对 connect 和 isConnected 的运行时有什么影响？

第二种方式更可取，因为它的高度只有 2，而不是 3。根据我们的新规则，我们也会选择第二种方式，因为 T2 比 T1 小（T2 的大小为 3，而 T1 为 6）。

我们通过树中的元素数量来确定大小关系。因此，在连接两棵树时，我们需要知道它们的大小（或权重）。我们可以通过用 -(size of tree) 替换 -1 来将此信息存储在树的根节点中。

Maximum height: Log N

遵循上述规则可以确保任何树的最大高度为 Θ(log N)。N 是我们的不相交集合中的元素数量。由此推及， **connect** 和 **isConnected** 的运行时间均受 O(log N) 的限制。

有关为什么是$logn$的证明：

为什么是 $\log N$？

下面提供一个可选的数学解释，说明为什么树的最大高度是
$$
\log_2 N.
$$

设想树 $T_1$ 中的任意一个元素 $x$。
元素 $x$ 的深度只会在一种情况下增加 1：当树 $T_1$ 被放到另一棵树 $T_2$ 的下面时。

而一旦发生这种情况，合并后得到的新树的规模至少会是 $T_1$ 规模的两倍，因为
$$
\text{size}(T_2) \ge \text{size}(T_1).
$$

包含元素 $x$ 的这棵树，在总元素数达到 $N$ 之前，最多只能发生如下次数的“翻倍”：
$$
\log_2 N,
$$
因为
$$
2^{\log_2 N} = N.
$$

因此，这样的翻倍过程最多发生 $\log_2 N$ 次；而每发生一次翻倍，树的高度就增加一层。
所以，这棵树的最大高度就是
$$
\log_2 N.
$$

你可能想知道为什么我们不根据高度而不是权重来链接树。事实证明，这更复杂来实现，并且仍然给我们相同的Θ(log N)高度限制。

Weighted Quick Union with Path Compression

巧妙之处在于意识到每当我们调用 find(x) 时，都必须从 x 到根遍历路径。因此，在途中我们可以将所有访问到的项连接到它们的根，而不会产生额外的渐近成本。

在途中将所有项连接到根将有助于使我们的树在每次调用 find 时变得更短。

回想起来， **connect(x, y)** 和 **isConnected(x, y)** 总是调用 **find(x)** 和 **find(y)** 。因此，在调用 connect 或 isConnected 足够次数后，基本上所有元素都会直接指向它们的根。

由此推论， connect 和 isConnected 的平均运行时间在长期内几乎变得恒定！这被称为摊还运行时间。

更具体地说，对于在 $N$ 个元素上执行的 $M$ 次操作，
带路径压缩的加权并查集（WQU with Path Compression）的时间复杂度为
$$
O!\left(N + M(\lg^* N)\right).
$$

其中，$\lg^* N$ 表示迭代对数（iterated logarithm）。
对于任何现实世界中的输入规模，$\lg^* N$ 的值都小于 $5$。
